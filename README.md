# Sivi-Pet

Привет! Это мой учебный пет-проект. Я хотел попробовать, как вообще работать
с API языковой модели, сделать чат с историей, поиск по своим заметкам (RAG),
проверку качества ответов и простое окошко на PyQt5.

Подробный разбор кода по файлам лежит в [GUIDE.md](GUIDE.md).

Модель запускается локально в LM Studio, а код стучится к ней по адресу
`http://localhost:1234/v1/chat/completions`.

Вот как это выглядит вживую. Я спросил про статистику, и видно, что
ответ пришёл из моих заметок в папке `data`.

## Что умеет

- общаться с моделью и помнить историю, она лежит в json и не теряется после перезапуска
- держать несколько профилей с разными системными промптами, у каждого своя история
- искать по моим заметкам, если модель попросит контекст
- работать и в консоли, и в окошке, логика у них общая
- проверять качество ответов: метрики поиска по golden set и оценка судьёй
  (та же модель, но в отдельном контексте)
- работать без поиска, если не ставить тяжёлые библиотеки

## Что где лежит

```
core/
  lm_client.py        клиент к модели, разбор ответа и ошибок
  history_manager.py  история, автосохранение, профили
  rag_manager.py      читает data/*.md, считает эмбеддинги, ищет похожее
  tool_manager.py     ищет в ответе модели маркер [RAG: ...]
  chat_engine.py      один ход диалога, общий для консоли и окошка
eval/
  golden_set.json     вопросы, эталоны и ожидаемые источники
  metrics.py          метрики поиска, считаются без модели
  judge.py            судья: рубрика, отдельный контекст, разбор вердикта
  run_eval.py         прогон golden set, отчёты в eval/results/
  make_drafts.py      черновики вопросов по заметкам
gui/
  chat_window.py      само окошко
main_console.py       чат в консоли
test.py               проверки, без модели, если не добавить --live
data/                 сюда кладу свои заметки, демо-набор лежит в git
profiles.json         системные промпты
history.json          история диалога, в git не попадает
```

## Как запустить

```bash
python -m venv venv
venv/Scripts/activate
pip install -r requirements.txt
```

Потом запускаю саму программу:

```bash
python main_console.py
python gui/chat_window.py
```

И проверки:

```bash
python test.py
python test.py --live
```

Перед запуском надо открыть LM Studio и загрузить модель, пусть висит на
порту 1234. Если порт другой, адрес меняется в `core/lm_client.py`.
Если в LM Studio загружено несколько моделей, в запросе нужно указывать её id,
иначе сервер вернёт ошибку 400.

В консоли есть команды: `выход`, `забудь всё`, `раг вкл` и `раг выкл`.

## Про поиск по заметкам

В папку `data` я кладу обычные `.md` файлы со своими заметками. Демо-набор
про LLM лежит в репозитории, он же используется для проверок качества. Личные
заметки по умолчанию в git не попадают: `data/` игнорируется, а демо-файлы
разрешены явными строками в `.gitignore`.

Дальше всё просто. Файлы режутся на кусочки по 500 символов с перекрытием 50,
кусочки превращаются в эмбеддинги моделью `intfloat/multilingual-e5-small`
и складываются в ChromaDB. Считается всё при первом поиске, чтобы окошко
открывалось быстро. Коллекция живёт в памяти, так что при каждом запуске
собирается заново.

Искать можно двумя способами.

1. Модель сама решает, когда ей нужны заметки. Тогда она отвечает строкой
   `[RAG: запрос]`, я это вижу и подставляю найденное.
2. Я включаю галочку "Искать в базе знаний" в окошке или пишу `раг вкл`
   в консоли. Тогда поиск идёт по тексту моего сообщения и всегда, ещё
   до ответа модели.

Второй способ мне понравился больше. Модель часто считает, что и так всё знает,
и в поиск не идёт. А когда идёт, то пишет в маркер целый абзац вместо вопроса.
С галочкой запрос уходит один вместо двух, и отвечает всё быстрее.

Ещё я отсекаю неподходящие кусочки по порогу `MAX_RELEVANT_DISTANCE = 0.34`
в `rag_manager.py`. Для своих заметок расстояние получалось около 0.3,
а для посторонних вопросов больше 0.36, поэтому порог как раз между ними.
Если ничего не подошло, модель отвечает своими знаниями, а в статусе видно,
что поиск ничего не дал. Прогон eval показывает среднее расстояние для
вопросов с ответом и для посторонних, так что порог можно перепроверить.

## Про проверку качества

Проверки в `test.py` следят за логикой, но не за качеством: они не скажут,
нашлась ли нужная заметка и верен ли ответ. Для этого есть папка `eval`.

В `eval/golden_set.json` лежат вопросы с эталонами, сейчас их 26. У каждой записи
есть тип: `answerable` (ответ есть в `data/`), `open` (в базе нет, но модель может
ответить сама) и `unanswerable` (данных нет нигде, жду честное "не знаю").
Ещё указаны `expected_sources` — по ним считаются метрики поиска.

Проверка идёт двумя слоями.

- **Метрики поиска** считаются без модели: нашёлся ли нужный файл в первых
  `top_k`, на каком месте, сколько релевантных фрагментов. Это `hit@k`,
  `recall@k`, `MRR` и `precision@k`.
- **Судья** это та же модель, но с отдельным контекстом. На каждый вопрос
  собирается новый список сообщений, без истории диалога и без системного
  промпта Sivi, температура 0. Судья возвращает JSON с оценкой, вердиктами
  `correct`, `grounded`, `relevant` и короткой причиной.

Запуск:

```bash
python eval/run_eval.py --model qwen/qwen3.5-9b
python eval/run_eval.py --no-judge      # только метрики поиска
python eval/run_eval.py --limit 3       # первые три вопроса
```

Отчёт складывается в `eval/results/` в двух видах: Markdown для чтения и JSON
для сравнения прогонов. В консоли ответ модели и вердикт судьи напечатаны
разными цветами, чтобы не смешивались.

Вопросы можно не придумывать вручную, а сгенерировать черновики по заметкам:

```bash
python eval/make_drafts.py --per-file 2
```

Это именно черновики, их надо вычитать: модель может придумать факт, которого
в заметке нет. Подходящие записи переносятся в `golden_set.json`.

В окошке есть кнопка "Оценить". Она прогоняет судью по последнему ответу и
показывает вердикт отдельным цветным блоком. Эталон там не передаётся, поэтому
судья смотрит только на вопрос, ответ и найденные фрагменты.

## Что я понял по ходу дела

- Никакие специальные вызовы инструментов не нужны, подойдёт обычная модель.
  Она просто пишет текстом `[RAG: запрос]`, а разбираю это уже я.
- `saiga_nemo_12b_gguf` отвечает на такой запрос за полминуты, а
  `qwen/qwen3.5-9b` слишком много думает, по итогу ответ около трёх минут.
- Reasoning-модели тратят кучу токенов на размышления. Если поставить
  маленький `max_tokens`, ответ приходит пустой. Поэтому по умолчанию стоит
  8192 и таймаут 300 секунд.
- Для оценки качества хватает одной модели, если запускать её вторым заходом
  с отдельным контекстом. Судья не должен видеть историю диалога, иначе он
  оценивает разговор, а не ответ.
- Судья тоже ошибается и иногда хвалит свои ответы. Поэтому рядом с оценкой
  всегда стоит держать метрики поиска и числа, а не верить только вердикту.
- В окошке `torch` надо импортировать до PyQt5. Иначе на Windows я ловил
  ошибку `WinError 1114` на `c10.dll` и поиск в окошке не работал.
  Порядок импорта это лечит.
- Результат поиска отправляю ролью `user`, а не `system`. С `system` посередине
  диалога LM Studio отвечает ошибкой 400.
- Историю сохраняю через временный файл. Так она не побьётся, если закрыть
  приложение в неудачный момент, а испорченный json не роняет запуск. Возможно кнопка сохранения теперь рудимент.

## Что можно было бы доделать

- показывать в окошке, какие именно заметки нашлись
- запоминать индекс на диск, чтобы не считать его каждый раз
- не давать модели пихать абзац в `[RAG: ...]`, а брать оттуда только вопрос
- расширять golden set по мере появления новых заметок
- сравнивать прогоны между собой и сохранять историю метрик
